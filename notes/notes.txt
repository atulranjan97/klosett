##################### Zod validation and type inference #######################################
We've been using .ts and .tsx file, we're using TS but we haven't utilized it to it's full potential.
for example, uptil now in our components -> shared -> `product-card.tsx` component we use the `any` type for product, which we shouldn't do, we should have a product type like 
    const ProductCard = ({ product }: {product: Product}) => {...}
So we're gonna create types, but we're also going to use a library called `Zod`.
so, Zod is a TS-first schema validation with static type inference. so not only does it cover types, it also offers runtime validation
If you just use TS on its own and you create your types or interfaces, that's great for development.
It offers compile time checking of your types, but it doesn't offer runtime validation for data from like APIs or forms. So, what this does is it allows us to create validation schemas so that we don't have to manually put validation like in our component or action that says like the name should have atleast three characters. Like we don't wanna clutter our code up with that, so we can just isolate it all inside of one file, inside of what's called a `Zod schema`.
And we can have schema for inserting products, for fetching products, deleting products or users or orders or whatever the resource might be

तुम्हारे project में तुम Prisma ORM का use करके PostgreSQL database से `Product` data fetch कर रहे हो। जब Prisma database से data लाता है, तब वह normal JavaScript object जैसा दिखाई देता है, लेकिन internally कुछ fields special Prisma objects होती हैं। तुम्हारे `Product` schema में `price` और `rating` fields `Decimal` type की हैं, इसलिए Prisma इन्हें normal JavaScript `number` के रूप में नहीं बल्कि `Prisma.Decimal` object के रूप में return करता है। Prisma ऐसा इसलिए करता है क्योंकि JavaScript decimal calculations में precision errors आ सकते हैं, जैसे `0.1 + 0.2 = 0.30000000000000004`। Financial values और ratings जैसी decimal values को accurately handle करने के लिए Prisma special Decimal object use करता है ताकि exact precision बनी रहे।

Backend के अंदर यह Decimal object ठीक से काम करता है और Prisma इसके methods भी देता है, लेकिन problem तब आती है जब data को frontend, API response, Next.js Server Components, Client Components, server actions, या `JSON.stringify()` के through भेजना होता है। Next.js और JSON serialization केवल plain serializable values समझते हैं जैसे string, number, boolean, array और plain object। लेकिन Prisma Decimal एक custom class/object होता है, इसलिए कभी-कभी serialization errors, hydration issues या weird object structures दिखाई दे सकते हैं। इसी problem को avoid करने के लिए `convertToPlainObject()` function बनाया जाता है।

```ts id="7t1xk5"
export function convertToPlainObject<T>(value: T): T {
  return JSON.parse(JSON.stringify(value));
}
```

इस function में पहले `JSON.stringify(value)` Prisma result को JSON string में convert करता है। इस step में Prisma के special internal objects simple serializable values में बदल जाते हैं। उसके बाद `JSON.parse()` उस JSON string को वापस plain JavaScript object में convert कर देता है। इसका मतलब final output में Prisma internals नहीं रहते और object safely frontend या Next.js components में भेजा जा सकता है। उदाहरण के लिए `Decimal("999.99")` convert होकर `"999.99"` बन जाता है जो plain serializable value है।

इस function में `<T>` TypeScript generic है। इसका मतलब function किसी भी type का data accept कर सकता है और वही type return करेगा। अगर input `Product[]` है तो output भी `Product[]` माना जाएगा। इससे TypeScript type safety बनी रहती है और autocomplete भी सही काम करता है।

तुम्हारे specific case में conversion mainly इसलिए जरूरी है क्योंकि schema में `price Decimal` और `rating Decimal` fields मौजूद हैं। बाकी fields जैसे `String`, `Int`, `Boolean`, `String[]` आदि पहले से plain JavaScript compatible हैं और उन्हें convert करने की जरूरत नहीं होती। `createdAt` field `DateTime` है जो JavaScript `Date` object के रूप में आता है और अधिकतर cases में Next.js इसे automatically serialize कर देता है, इसलिए उसके लिए usually extra handling की जरूरत नहीं पड़ती।

Practical rule यह है कि अगर Prisma data केवल backend logic में use हो रहा है तो conversion optional है। लेकिन अगर वही data frontend, React components, API response, server action return value, cache, localStorage या network response में जा रहा है, तो उसे plain serializable object में convert करना recommended और safer approach है। इसलिए तुम्हारे Next.js + Prisma project में `convertToPlainObject()` use करना एक common और practical pattern है।

    ── WHY `any` TYPE? ─────────────────────────────────────────

    Normally TypeScript mein `any` use karna bad practice hai
    kyunki yeh type safety tod deta hai — matlab TypeScript
    koi bhi check nahi karta aur galtiyan runtime pe aati hain.

    Lekin yahan `any` use kiya hai kyunki:

      - `error` ka type predict nahi hota — kabhi ZodError,
        kabhi PrismaClientKnownRequestError, kabhi kuch aur

      - Proper types laana (z.ZodError | Prisma.PrismaClientKnownRequestError | Error)
        bahut complex aur confusing ho jaata beginners ke liye

      - Yeh un "rare occasions" mein se ek hai jahan `any`
        practically sahi choice hai

    ── WHY eslint-disable COMMENT? ─────────────────────────────

    ESLint ek code quality tool hai jo tumhara code check karta hai.
    Iska ek rule hai: `@typescript-eslint/no-explicit-any`
    Yeh rule `any` likhne pe ERROR throw karta hai.

    LOCAL (tumhara laptop): koi problem nahi, code chal jaata hai

    VERCEL (production deploy): Vercel build ke time ESLint
    strict mode mein run karta hai — `any` milne pe BUILD FAIL
    ho jaati hai aur deploy nahi hota:
      ❌ Error: Unexpected any. Specify a different type.
      ❌ Failed to compile.

    SOLUTION: Yeh comment ESLint ko bolta hai —

## 1. PrismaAdapter automatically User + Account create karta hai

Jab koi pehli baar Google se login karta hai, PrismaAdapter **automatically** ye karta hai:

```
Google se aata hai:
{
  name: "Atul Kumar",
  email: "atul@gmail.com",
  picture: "https://..."
}
```

Prisma adapter ye **automatically** DB mein dalta hai:

```sql
-- User table mein
INSERT INTO User (name, email) VALUES ('Atul Kumar', 'atul@gmail.com')

-- Account table mein (Google account link karta hai)
INSERT INTO Account (userId, provider, providerAccountId) 
VALUES (userId, 'google', 'google-user-id-123')
```

**Tum kuch nahi likhte** — adapter khud karta hai. Isliye `signUpUser` jaisi koi function nahi banani Google ke liye.

---

## 2. JWT strategy mein Adapter sirf Google linking ke liye

Do strategies hoti hain NextAuth mein:

```
Database Strategy:
  Login → Session DB mein save hoti hai → Har request par DB check hota hai

JWT Strategy (tumhari):
  Login → Token browser cookie mein save hota hai → Har request par sirf token check hota hai, DB nahi
```

Toh adapter ka kaam sirf itna hai:

```
JWT Strategy mein Adapter:
✅ Google user pehli baar aaya → User + Account DB mein banao
✅ Dobara aaya → Account table se dhundo, user identify karo
❌ Session DB mein save nahi karta (JWT kar raha hai ye kaam)
```

---

## 3. Role Google se nahi aata, DB se lena padta hai

Google sirf ye deta hai:
```js
profile = {
  name: "Atul Kumar",
  email: "atul@gmail.com",
  picture: "https://...",
  email_verified: true
  // ❌ role nahi deta
}
```

Isliye JWT callback mein manually DB se fetch karte hain:

```ts
async jwt({ token, user, account }) {
  // Google login detect karo
  if (account?.provider === 'google') {
    const dbUser = await prisma.user.findFirst({
      where: { email: token.email! }
    });
    // DB se role lo
    token.role = dbUser?.role; // 'user' or 'admin'
  }

  // Credentials login mein role directly milta hai
  if (user) {
    token.role = user.role;
  }

  return token;
}
```

Flow kuch aisa hai:
```
Google Login
    ↓
Adapter: User DB mein banao (role default 'user' hoga)
    ↓
JWT Callback: DB se role fetch karo
    ↓
Session Callback: Token se role session mein daalo
    ↓
Frontend: session.user.role available hai
```

## 4. Production mein Redirect URI add karna

Development mein tumhara URL hota hai:
```
http://localhost:3000/api/auth/callback/google
```

Production mein hoga:
```
https://yoursite.com/api/auth/callback/google
```

Google **sirf registered URIs** par redirect karta hai — security ke liye. Agar add nahi kiya toh:

```
Error: redirect_uri_mismatch
Google aapki site ko nahi jaanta, block kar dega
```

Google Console mein jaake dono add karo:
```
✅ http://localhost:3000/api/auth/callback/google   (development)
✅ https://yoursite.com/api/auth/callback/google    (production)
```

> Adapter = Google user DB mein banata hai | JWT = Session manage karta hai | Role = DB se manually lena padta hai | Redirect URI = Google ko batao ki kaun sa URL trusted hai ✅

### NextAuth `authorized` Callback & Proxy — Notes

`authorized` ek **NextAuth callback** hai jo decide karta hai ki kisi bhi incoming request ko allow karna hai ya block karna hai. Yeh callback **har request pe** automatically invoke hota hai — chahe user `/dashboard` khole, `/profile` khole, ya koi bhi route — aur `request` object se `request.nextUrl.pathname` ke through pata chalta hai ki user kaun sa page open karna chahta hai. Callback ke andar `auth` object hota hai jisme logged-in user ki info hoti hai, aur `request` object hota hai jisme cookies, headers, aur URL hoti hai. Return value se decide hota hai kya karna hai — `true` matlab allow karo, `false` matlab `/sign-in` pe redirect karo, aur `NextResponse` return karo agar cookie set karni ho ya custom redirect karna ho.

**Lekin `authorized` akela kuch nahi kar sakta** — isko trigger karne ke liye `proxy.ts` (Next.js 16) ya `middleware.ts` (Next.js 15) zaroori hai. `proxy.ts` har incoming request ko intercept karta hai **page render hone se pehle** — aur jab hum `export { auth as proxy } from '@/auth'` likhte hain, toh NextAuth apna `auth` function proxy ke through run karta hai jo internally `authorized` callback invoke karta hai. Agar `proxy.ts` file hi nahi hai toh koi bhi request seedha page tak pahunch jayegi bina kisi check ke — protected routes bhi bina login ke khul jayenge aur guest cart ke liye `sessionCartId` cookie bhi kabhi set nahi hogi.

**Practical use cases:** Protected routes ke liye check karo ki `auth?.user` hai ya nahi — nahi hai toh `false` return karo. Role-based access ke liye check karo ki `auth?.user?.role === 'admin'` hai ya nahi. Guest functionality ke liye — jaise humara cart — `sessionCartId` cookie check karo, nahi hai toh `crypto.randomUUID()` se naya ID banao aur `NextResponse` mein cookie set karke return karo. **Yaad rakho** — `authorized` sirf **routing aur access control** ke liye hai, yahan heavy database calls ya business logic nahi daalni chahiye — woh kaam Server Components aur Server Actions ka hai. 🎯
